# 나만의 용돈 기입장 (Budget Project)

Python 표준 라이브러리를 활용하여 개발한 CLI(Command Line Interface) 기반 용돈 기입장 프로그램입니다.

수입과 지출을 기록하고, 카테고리별로 거래 내역을 관리하며, 월별 통계와 예산 사용 현황을 확인할 수 있습니다. 거래 내역은 JSONL 파일로 저장하고 CSV 파일로 가져오거나 내보낼 수 있습니다.

## 1. 개발 환경

- 언어: Python 3.12
- 개발 도구: Visual Studio Code
- 실행 환경: macOS 터미널
- 사용 라이브러리: Python 표준 라이브러리
- 데이터 저장 방식: JSONL
- 테스트 프레임워크: unittest

별도의 외부 패키지 설치 없이 실행할 수 있습니다.

## 2. 주요 기능

| 기능 | 설명 |
|---|---|
| 거래 등록 | 날짜, 수입·지출 유형, 카테고리, 금액, 메모, 태그 입력 |
| 거래 조회 | 최근 거래 내역 조회 및 출력 개수 제한 |

## 클래스별 역할과 책임

프로그램은 데이터 모델, 저장소, 서비스, CLI 계층으로 구분하여 각 구성 요소의 책임을 분리했습니다.

| 클래스 | 역할 | 인스턴스가 담당하는 데이터 및 행위 |
|---|---|---|
| `Transaction` | 거래 데이터 모델 | 거래 ID, 유형, 날짜, 금액, 카테고리, 메모, 태그 보관 |
| `TransactionRepository` | 거래 데이터 저장소 | `transactions.jsonl`의 거래 읽기, 추가, 수정, 삭제 및 ID 생성 |
| `CategoryStore` | 카테고리 저장소 | `categories.jsonl`의 카테고리 목록 조회, 추가, 삭제 |
| `BudgetRepository` | 예산 데이터 저장소 | `budgets.jsonl`의 월별 예산 조회 및 저장 |
| `TransactionService` | 거래 비즈니스 로직 | 거래 입력값 검증, CRUD, 검색, 월별 통계 계산 |
| `CategoryService` | 카테고리 비즈니스 로직 | 카테고리 중복 검증 및 사용 중인 카테고리 삭제 방지 |
| `BudgetService` | 예산 비즈니스 로직 | 예산 유효성 검증, 지출 집계, 사용률 및 잔액 계산 |

### Repository와 Service를 분리한 이유

**Repository**는 데이터를 어디에 어떻게 저장하고 읽을지 담당합니다. JSONL 파일 접근과 파일 갱신이 주요 책임입니다.

**Service**는 어떤 데이터를 허용하고 어떻게 계산할지 담당합니다. 거래 금액 검증, 카테고리 존재 여부 확인, 예산 사용률 계산 등이 주요 책임입니다.

예를 들어 거래를 등록할 때 `TransactionService`가 입력값을 검증한 후 `TransactionRepository`를 호출하여 파일에 저장합니다.

`cli.py`는 사용자 명령어를 해석하고 Service를 호출한 다음 결과를 출력합니다. 따라서 사용자 인터페이스, 업무 규칙, 데이터 저장 방식을 독립적으로 관리할 수 있습니다.

### CSV 가져오기의 원자성 및 오류 복구

CSV 가져오기 과정에서 일부 거래만 저장되는 문제를 방지하기 위해 일괄 저장 방식을 구현했습니다.

**처리 과정**

1. CSV 파일을 읽고 모든 거래의 유효성을 먼저 검사합니다.
2. 기존 거래 ID와 중복되는 항목은 건너뜁니다.
3. 검증을 통과한 신규 거래들을 `TransactionRepository.add_many()`로 전달합니다.
4. 기존 JSONL 데이터와 신규 거래를 임시 파일에 기록합니다.
5. 모든 기록이 성공하면 `os.replace()`로 원본 파일을 한 번에 교체합니다.
6. 교체 전 오류가 발생하면 임시 파일을 정리하고 기존 원본 파일은 유지합니다.

**오류 발생 시 동작**

| 상황 | 처리 결과 |
|---|---|
| CSV 데이터 검증 실패 | 저장하지 않고 오류가 발생한 행 안내 |
| 중복 거래 ID 발견 | 해당 거래 건너뛰기 |
| 임시 파일 기록 실패 | 원본 데이터 유지 |
| 최종 파일 교체 실패 | 원본 데이터 유지 |
| 모든 작업 성공 | 신규 거래 전체 저장 |

**자동화 테스트**

`test_import_rollback_on_replace_failure` 테스트에서는 `os.replace()`에 강제로 `OSError`를 발생시켜 파일 교체 실패 상황을 재현합니다.

이후 기존 JSONL 파일의 내용이 가져오기 이전과 완전히 동일하고, 신규 거래가 저장되지 않았음을 확인합니다.

현재 구현은 단일 파일의 원자적 교체를 보장하는 방식입니다. 여러 프로세스의 동시 쓰기나 전원 차단 상황까지 완전히 보호하는 트랜잭션 시스템은 아닙니다.

## 6. 데이터 저장 구조

데이터는 JSONL(JSON Lines) 형식으로 관리합니다.

JSONL은 한 줄에 하나의 JSON 객체를 저장하는 방식입니다.

거래 데이터 예시:

```json
{"id":"TX-000001","type":"expense","date":"2026-10-28","amount":15000,"category":"food","memo":"점심","tags":["meal"]}
```

주요 데이터 파일:

- `transactions.jsonl`: 거래 내역
- `categories.jsonl`: 카테고리
- `budgets.jsonl`: 월별 예산

거래 수정·삭제 등 일부 파일 갱신 작업에서는 임시 파일과 `os.replace()`를 사용하여 저장 과정의 안정성을 높였습니다.

### JSONL과 CSV 비교 및 선택 이유

| 비교 항목 | JSONL | CSV |
|---|---|---|
| 데이터 구조 | JSON 객체를 한 줄씩 저장 | 행과 열로 구성된 표 형태 |
| 데이터 타입 | 숫자, 문자열, 리스트 등 표현 가능 | 기본적으로 문자열 형태로 저장 |
| 태그 저장 | `["food", "meal"]`처럼 리스트로 저장 가능 | `"food,meal"`처럼 문자열로 변환 필요 |
| 데이터 추가 | 파일 끝에 JSON 객체를 한 줄씩 추가 가능 | 파일 끝에 새로운 행 추가 가능 |
| 데이터 확인 | 프로그램에서 구조화된 데이터 처리에 적합 | Excel 등 스프레드시트 프로그램에서 확인하기 편리 |
| 단점 | CSV보다 파일 크기가 커질 수 있음 | 리스트 등 복잡한 데이터 표현이 불편함 |

#### JSONL을 선택한 이유

이 프로젝트에서는 거래 내역을 저장할 때 **JSONL을 기본 데이터 저장 형식**으로 선택했습니다.

첫째, 거래 데이터에는 ID, 날짜, 금액뿐 아니라 여러 개의 태그를 담는 리스트가 포함되어 있어 JSONL이 데이터 구조를 표현하기에 적합합니다.

둘째, JSONL은 한 줄에 하나의 거래 객체를 저장하므로 파일 전체를 메모리에 올리지 않고 제너레이터를 이용해 거래 내역을 순차적으로 읽을 수 있습니다.

셋째, 새로운 거래를 등록할 때 기존 파일 전체를 다시 작성하지 않고 파일 끝에 한 줄을 추가할 수 있습니다.

반면 CSV는 Excel 등 외부 프로그램과 데이터를 주고받기 편리하므로 **가져오기·내보내기 기능에 사용**했습니다.

따라서 JSONL은 프로그램 내부의 데이터 저장에, CSV는 외부 데이터 교환에 사용하는 방식으로 역할을 구분했습니다.

- 수입·지출 유형
- 금액의 유효성
- 등록된 카테고리 사용 여부

- 검색 금액 범위

오류가 발생하면 가능한 경우 Python의 긴 예외 출력 대신 사용자가 이해할 수 있는 메시지를 표시합니다.

```text

[오류] 2행: 금액은 0보다 커야 합니다.
```

## 8. 데코레이터 활용

`decorators.py`에 함수 실행 시간을 측정하는 `measure_time` 데코레이터를 구현했습니다.

`@wraps`를 사용하여 원래 함수의 이름과 메타데이터를 유지하며, `time.perf_counter()`로 실행 시간을 측정합니다.

거래 검색과 월별 통계 함수에 적용했습니다.

출력 예시:

```text
[실행 시간] get_monthly_summary: 0.0022초
```

### 로깅 및 예외 처리 데코레이터

실행 시간 측정 외에도 로깅과 예외 처리를 공통 기능으로 분리했습니다.

| 데코레이터 | 책임 |
|---|---|
| `measure_time` | 함수 실행 시간 측정 |
| `log_execution` | 함수 실행 시작 및 정상 완료 로그 기록 |
| `handle_errors` | 예외 발생 시 오류 로그 기록 및 예외 재발생 |

`search_transactions()`에 세 데코레이터를 적용하여 검색 로직과 로깅·예외 처리·성능 측정 기능을 분리했습니다.

```python
@handle_errors
@log_execution
@measure_time
def search_transactions(...):
    ...
```

위 코드는 적용 구조를 설명하기 위한 예시이며, 실제 함수의 매개변수와 내부 구현은 생략했습니다.

예외 처리 데코레이터는 오류를 기록한 후 `raise`로 원래 예외를 다시 발생시킵니다. 따라서 기존 CLI의 사용자용 오류 메시지 처리 방식은 유지됩니다.

로깅은 Python 표준 라이브러리의 `logging`을 사용하며, `INFO` 로그는 로깅 설정에 따라 기본 터미널에 표시되지 않을 수 있습니다.


테스트 대상:

- 거래 등록 및 입력값 검증
- 거래 수정·삭제·검색
- 월별 통계 계산
- 예산 관리 및 잘못된 금액 처리
- CSV 내보내기·가져오기
- CSV 중복 거래 처리
- 존재하지 않는 CSV 파일 처리
- 데코레이터 반환값 및 출력 검증

현재 총 **20개의 자동화 테스트가 통과**했습니다.

```text
Ran 19 tests in 0.030s

OK
```

테스트에서는 `tempfile.TemporaryDirectory()`를 활용하여 실제 사용자 데이터에 영향을 주지 않도록 임시 저장소를 사용합니다.

## 대용량 데이터 처리 및 성능 분석

이 프로젝트는 JSONL 파일을 기반으로 거래 데이터를 저장하고 있으며, 10만 건(100,000건) 이상의 거래가 저장될 경우를 고려하여 예상 병목 지점과 개선 방안을 분석했습니다.

### 1. 주요 기능별 시간 및 메모리 복잡도

거래 건수를 `N`, 조회할 최근 거래 건수를 `K`라고 가정합니다.

| 기능 | 시간 복잡도 | 메모리 특성 |
|---|---|---|
| 거래 추가 | 일반적으로 O(1) | 거래 1건 처리 |
| 전체 거래 순회 | O(N) | 제너레이터 사용 시 O(1) 추가 메모리 |
| 최근 K건 조회 (`heapq.nlargest`) | O(N log K) | O(K) |
| 조건별 검색 | O(N) | 검색 결과를 리스트로 모으므로 최악 O(N) |
| 월별 통계 | O(N) | 카테고리별 집계 데이터 저장 |
| 거래 ID 검색 | O(N) | 순차 검색 |
| 거래 수정·삭제 | O(N) | 임시 파일에 전체 데이터 재작성 |

※ 위 복잡도는 현재 JSONL 파일을 순차적으로 처리하는 구조를 기준으로 한 이론적 분석이며, 실제 측정 결과는 아닙니다.

### 2. 예상되는 성능 병목

**① 파일 I/O 증가**

거래 내역이 10만 건 이상으로 증가하면 검색, 통계, 수정·삭제 과정에서 많은 데이터를 읽거나 다시 기록해야 합니다.

특히 거래 수정·삭제는 임시 파일을 생성하여 기존 데이터를 다시 작성하므로 디스크 I/O 비용이 증가합니다.

**② 거래 ID 조회의 비효율**

현재는 거래 ID를 이용해 특정 거래를 찾을 때 파일을 순차적으로 검색합니다. 따라서 데이터가 증가할수록 조회 시간이 길어질 수 있습니다.

**③ 검색 결과의 메모리 사용량**

`get_all()`은 제너레이터를 사용하므로 거래 데이터를 한 번에 모두 메모리에 올리지 않습니다.

하지만 검색 결과를 리스트로 수집하면 조건에 맞는 거래가 많을수록 메모리 사용량이 증가합니다.

**④ 최근 거래 조회의 연산 비용**

`heapq.nlargest()`를 사용하면 전체 거래를 정렬하는 방식보다 적은 메모리로 최근 K건을 선택할 수 있습니다.

그러나 최근 K건만 조회하더라도 전체 JSONL 파일을 읽어야 하므로 거래 건수가 증가하면 처리 시간도 늘어납니다.

### 3. 개선 방안 및 우선순위

| 우선순위 | 개선 방안 | 기대 효과 |
|---|---|---|
| 1순위 | 거래 데이터 저장소를 SQLite로 전환하고 날짜·ID에 인덱스 적용 | 검색, 조회, 수정·삭제 성능 개선 |
| 2순위 | 검색 결과에 페이지네이션 적용 | 대량 검색 시 메모리 사용량 감소 |
| 3순위 | 월별 통계 결과 캐싱 또는 사전 집계 | 반복적인 통계 조회 비용 감소 |
| 4순위 | 대용량 데이터 벤치마크 테스트 추가 | 실제 병목 확인 및 개선 효과 검증 |

### 4. 현재 구현의 장점과 한계

현재 구조는 Python 표준 라이브러리만으로 구현할 수 있고, 파일을 직접 확인하기 쉬우며, 제너레이터를 활용한 순차 처리가 가능합니다.

다만 데이터가 증가할수록 전체 파일을 순회해야 하는 작업의 비용이 커집니다.

따라서 소규모 개인 용돈 기입장에서는 JSONL 구조를 유지하되, 거래가 10만 건 이상으로 증가하고 검색·수정 작업이 빈번해진다면 SQLite와 인덱스 기반 구조로 전환하는 것이 적합합니다.

실제 10만 건 데이터에 대한 벤치마크는 아직 수행하지 않았으며, 위 내용은 현재 코드 구조를 기준으로 한 예상 성능 분석입니다.
